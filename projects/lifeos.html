The problem

I was managing my life across six different tools: a spreadsheet for finances, Notion for habits, a notes app for health logs, separate trackers for fitness and reading, and nothing at all connecting them. Every week I'd wonder the same questions — am I on budget? Did my sleep affect my productivity? What does an optimal meal plan look like given this month's grocery budget? — but the data to answer them lived in six different places.

The problem wasn't data. I had plenty of it. The problem was that each domain was a silo, so cross-domain insight was impossible. I couldn't see how a spending spike in one category compressed my food budget, or how my workout frequency correlated with mood scores. The answer wasn't a better note-taking app — it was a single platform where all six domains shared the same data layer.

Key decisions

01
LP macro optimizer for nutrition

Most nutrition apps track what you ate. This one tells you what to eat. A linear programming solver (Python + Flask) takes your weekly budget, protein target, calorie limit, and a list of available foods, then returns the minimum-cost meal plan that satisfies every constraint. The binding-constraint analysis shows exactly which constraint is limiting — if you want more protein, it shows whether that means spending more money or cutting calories.

02
Event-driven architecture for cross-domain consistency

Each domain publishes events when state changes — a logged expense emits a budget-updated event; a workout completion emits a recovery-metric-changed event. Other domains subscribe and update accordingly. This means the finance module can tighten the nutrition budget automatically after an unexpected expense, without the nutrition module knowing anything about finance. Loose coupling, cross-domain reactivity.

03
Flask for computation, Next.js for UI

The LP solver, regression models for trend analysis, and the CNN emotion classifier all live in Flask — computation-heavy tasks that don't belong in the browser or a Next.js API route. Next.js handles SSR for the dashboard and all UI state. The split lets each layer do what it's best at: Flask for numerical work, Next.js for fast page loads and React component trees.

04
PostgreSQL over NoSQL — analytics wins over flexibility

The finance module started as a standalone Python/Flask app 5+ years ago. That history matters: with years of transactions, workouts, and habit streaks in the database, the queries that provide insight are all time-series joins and aggregations — things relational databases handle well. A document store would have required materialising these joins in application code. PostgreSQL lets me ask cross-domain questions directly in SQL.
